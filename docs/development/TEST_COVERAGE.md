## Additional safeguards and UI assertions

[Knowledge worker tests](../../tests/worker/knowledge.test.ts) assert exact primary-entity mapping rather than links/mentions, original text boundaries and hashes, canonical-URL collisions, explicit derived rights-page URLs, unsafe URL rejection, inert hostile prose, bounded detail downloads and exact slug/URL/brand/year validation. Deduplication preserves different numeric claims instead of hashing search tokens that discard short numbers. Search results remain unreviewed local excerpts, not approved model answers.

[Knowledge database tests](../../tests/database/knowledge.test.ts) run real isolated PostgreSQL for transactional manifest staging, idempotent replay, explicit parser revisions, rollback on injected failure with safe error output, bounded/nonoverlapping document spans, deferred completeness constraints, immutable history and role isolation. The tables contain metadata only; full source documents stay in private Storage. Tests assert that staging leaves source rights pending and the published catalogue unchanged. Separate cloud staging produced 31 private assets / 618 document manifests; this is not a retrieval benchmark or a release.

[Database tests](../../tests/database/ingestion.test.ts) additionally assert that a worker role cannot directly alter the active pointer or publication audit, reset release status to draft, mutate pinned evidence or approve an unbacked projection. Explicit review can rebuild a draft; approval freezes its lineage. These assertions protect the release gate itself rather than only its happy path.

[Reprocessing regressions](../../tests/review/reprocessing.test.ts) protect the distinction between immutable raw input and a parser's versioned interpretation. A repaired parser must not inherit a stale source URL/ID from the first failed interpretation; a new interpretation must not rewrite a legacy published release. Provenance corrections count as semantic changes, and duplicate-ID checks use the run selected for publication. All three cases execute against isolated local PGlite databases.

[Web unit tests](../../tests/web/catalogue.test.ts) cover query length/page bounds, shareable filters, missing values, raw numeric zero/object rendering, source-link sanitation, unverified manufacturer labels and dedicated database login/TLS validation. [Server tests](../../tests/web/catalogue-server.test.ts) distinguish explicit fixtures, missing configuration, failed reads and legitimately empty released data.

[Profile rendering](../../tests/web/profile-render.test.ts) calls the actual profile component and React server renderer with a mocked catalogue. It asserts that extensible source fields named like inherited JavaScript properties render as plain labels rather than resolving to prototype objects/functions. This is a regression check for a profile crash, not a browser or cloud integration test.

[Browser tests](../../tests/web/catalogue.spec.ts) cover keyboard skip navigation, filtering to the exact year/variant, profile provenance, a missing profile, empty search, unknown year, visible conflicts, desktop/mobile/landscape overflow and automated axe WCAG A/AA checks. Screenshots are generated by that suite. Their existence or test implementation alone is not a passing result or complete manual accessibility audit. Impeccable review is not claimed.

## Reproduction

From the repository root after `npm ci`:

```text
npm run typecheck
npm run lint
npm test
npm run build
npm run test:e2e
npm run worker -- profile --source padeltrue --file tests/fixtures/padeltrue.synthetic.json
npm run worker -- import --source padelhow --file tests/fixtures/padelhow.synthetic.json --dry-run
npm run worker -- demo
npm run knowledge -- profile --file "sources/LLM FULL TEXT.txt" --catalogue sources/rackets.json
```

The browser suite requires the browser selected by `playwright.config.ts` (default: installed Microsoft Edge). CI installs Chromium and sets `PLAYWRIGHT_CHANNEL=chromium`; see [SETUP](SETUP.md#testy) for cross-platform commands. `demo` writes only the explicitly local `.local/worker` state, imports a separate clean synthetic fixture and demonstrates local publication. It never stages or publishes a cloud catalogue. Stop the worker before resetting/backing up persistent PGlite state; do not share a directory between concurrent processes. See [database operations](../../supabase/README.md).

For focused runs use `npm test -- tests/domain`, `npm test -- tests/database`, `npm test -- tests/worker`, `npm test -- tests/review` or `npm test -- tests/web`. The knowledge profile command requires owner-supplied private files; CI does not fetch or receive them. With confirmed Dev credentials, `npm run worker -- check-storage` performs the separate bounded HTTP probe; optional `SUPABASE_PUBLISHABLE_KEY` enables the anonymous-role portion. Record exact command, environment, outcome and skips in the current report. A local test run must not be reported as Supabase Cloud success.

## Evidence still required before claiming a real imported catalogue

- Source permission scope for actual inputs; no assumptions about private correspondence or unrestricted article/image reuse. Development project identity has been confirmed.
- Explicit review of actual staged completeness/exceptions/diff, exact identities and a separately approved release. No partial failed snapshot may be presented as a complete catalogue. Source file delivery and successful private Storage writes do not override this gate.
- A Next.js walkthrough of a nonempty approved release, plus isolated development-only failure/rollback checks where authorized. The restricted reader connection and genuinely empty cloud-backed UI have already been verified.
- For a future assistant: evidence-grounded retrieval benchmarks, Polish/English cases and prompt-injection/citation checks. Local keyword audit search and private manifests do not establish runtime RAG quality.

Actual input availability, full profiling and both-bucket HTTP verification are no longer missing-access blockers.
